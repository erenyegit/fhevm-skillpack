## Wire format

When the frontend wants to send an encrypted value to a contract, it
encrypts under the FHEVM public key and produces two artifacts:

- `externalEuintXX` — a `bytes32` wire handle (one per encrypted slot)
- `bytes inputProof` — a zero-knowledge proof of well-formedness, bound to
  `(contractAddress, userAddress)`

The contract receives these as parameters and validates by calling
`FHE.fromExternal(externalEuintXX, inputProof)`.

## Frontend flow

```ts
import { useEncrypt } from "@zama-fhe/react-sdk";
import { bytesToHex } from "viem";

const encrypt = useEncrypt();

const enc = await encrypt.mutateAsync({
  values: [
    { value: BigInt(amount),   type: "euint64" },
    { value: BigInt(beneficiary), type: "eaddress" },
  ],
  contractAddress: token.address,   // ← bound here
  userAddress: address,             // ← and here
});

await writeContractAsync({
  address: token.address,
  abi: token.abi,
  functionName: "depositFor",
  args: [
    bytesToHex(enc.handles[0]!),   // first value
    bytesToHex(enc.handles[1]!),   // second value
    bytesToHex(enc.inputProof),    // single proof for both
  ],
  gas: 15_000_000n,
});
```

`enc.handles` is an array — one per `values` entry. `enc.inputProof` is a
single proof covering all values in the input.

Hardhat-side equivalent for tests:
```ts
const input = fhevm.createEncryptedInput(token.address, alice.address);
input.add64(BigInt(amount));
input.addAddress(beneficiary);
const enc = await input.encrypt();
```

Foundry-side (forge-fhevm) test helper for a single value:
```solidity
(externalEuint64 enc, bytes memory proof) = encryptUint64(amount, alice, address(token));
```

## Contract entry

```solidity
function depositFor(
    externalEuint64 encAmount,
    externalEaddress encBeneficiary,
    bytes calldata inputProof
) external {
    euint64 amount = FHE.fromExternal(encAmount, inputProof);
    eaddress beneficiary = FHE.fromExternal(encBeneficiary, inputProof);
    // ... apply
}
```

`FHE.fromExternal` does two things:
1. Verifies the proof binds to `(address(this), msg.sender)` *as encrypted*.
2. Returns an internal handle that the contract has ACL access to.

## Third-party caller risk

The proof binds to the **encrypter's** address — typically the user who
generated the encrypted input in the browser. If the contract relies on
`msg.sender` to identify the source of funds:

```solidity
function deposit(externalEuint64 enc, bytes calldata proof) external {
    euint64 amount = FHE.fromExternal(enc, proof);   // bound to whoever encrypted
    _balances[msg.sender] = FHE.add(_balances[msg.sender], amount);
    //                ^^^^^^^^^^ assumed = encrypter, but might be a relayer
}
```

If a relayer or attacker captures Alice's `(enc, proof)` tuple from the
mempool, they can call `deposit` themselves with the same args. The proof
still validates (it was generated by Alice for `address(this)` — the proof
is not bound to the caller of the function). Now `_balances[attacker]`
increases.

## Three mitigations

### (a) Bind to `msg.sender` via the encrypted input itself

Have the frontend also encrypt the user's address and check it in the
contract:

```solidity
function deposit(
    externalEuint64 encAmount,
    externalEaddress encSender,
    bytes calldata proof
) external {
    euint64 amount  = FHE.fromExternal(encAmount, proof);
    eaddress claimedSender = FHE.fromExternal(encSender, proof);
    ebool ok = FHE.eq(claimedSender, FHE.asEaddress(msg.sender));
    // No-op the deposit if mismatch
    _balances[msg.sender] = FHE.select(ok,
        FHE.add(_balances[msg.sender], amount),
        _balances[msg.sender]
    );
    FHE.allowThis(_balances[msg.sender]);
    FHE.allow(_balances[msg.sender], msg.sender);
}
```

### (b) Per-user nonce in calldata + signature

Have the encrypter sign `(amount, nonce, contract)` with their EOA key.
Validate signature in the contract; reject stale nonces.

### (c) Single-shot consumption

Maintain `mapping(bytes32 proofHash => bool used)` and reject reused proofs.
Higher gas; cheapest defense for high-value flows.

## Notes

- Proofs do not survive across contracts: an `(enc, proof)` tuple generated
  for contract A cannot be replayed against contract B (proof binds to
  `address`).
- For batch inputs, use a single proof covering many values to amortize
  proof generation cost.
- Hardhat's `fhevm.createEncryptedInput` and Foundry's `encryptUintXX` /
  `encryptAddress` helpers both produce the same wire format.
